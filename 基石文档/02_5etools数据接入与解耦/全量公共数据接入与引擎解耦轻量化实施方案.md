# 全量公共数据接入与引擎解耦轻量化实施方案

> **版本**：v3.0（可执行与可验收修订版）
>
> **修订日期**：2026-09-25
>
> **状态**：步骤 1–8 已实施；2026-09-25 最终验收为“工程与真实双源链路通过，受验收浏览器网络策略限制的交互项待普通浏览器复核”。详见《最终全链路验收报告.md》。
>
> **内容依据**：[tjliqy/5etools-cn](https://github.com/tjliqy/5etools-cn) 与 [tjliqy/homebrew](https://github.com/tjliqy/homebrew)。

## 一、目标、范围与原则

本项目以两个公共仓库为职业、子职业、扩展特性、法术和装备等规则内容的依据，以自研向导和引擎负责选择、校验、计算、人工覆盖及 Calculation Trace。资源覆盖范围不能以本地已录入的核心职业名单为边界。

1. **公共内容优先**：本地 src/data/、src/data-legacy/ 仅在迁移期间承担明确标示的离线兜底和旧角色兼容，不能作为扩展资源的完整清单。
2. **原文完整保留**：保存 raw、entries、书源和文件来源；标签解析仅改变展示形式，不改写原文、不自行翻译，不用本地文案覆盖远程内容。未知标签提供可读回退。
3. **自研计算独立**：机制适配对应明确的公共条目和版本；Overlay 只补充机器可读规则，不重新维护一套完整内容库。
4. **显式规则选择**：保留 2014/2024 的来源区分和独立兼容开关，不自动以新版本替换旧规则。Homebrew 版本不能仅凭书源前缀或出版年份判断。
5. **人工裁决优先**：玩家/DM 的手动值最后生效，保留系统推导值和来源。修改展示值时，相关派生数值也应按规则重新计算。
6. **逐步汇报**：每完成一个可验收步骤，用中文说明改动、证据、限制和下一步；不把“注册成功”或“单元测试通过”称为“全量可用”。

### 1.1 “全量”的范围

本轮目标类别：职业、子职业、职业特性、子职业特性、可选特性、种族与亚种、背景、专长、法术、普通与魔法装备、工具、魔法变体、黑暗赠礼、超自然赠礼、恩惠、祝福及必要的规则元数据。

怪物、冒险全文、图片和音视频不属于本轮必须全量加载的范围；若建卡条目引用其中的必要内容，应记录依赖并按需处理。Homebrew 的 collection 等集合目录也必须检查，不能只扫描与类别同名的目录。

全量可发现不要求首屏下载全部资源。允许用户启用资源包并按类别增量加载，但目标资源应有完整发现路径，已启用包的必需依赖必须就绪。

### 2.2 五个完成层次

| 层次 | 验收条件 |
|---|---|
| 发现 | 能列出目标文件、包、来源和修订；分页与截断检查完成 |
| 载入 | 文件读取、缓存、解析和注册成功；失败可追查 |
| 关联 | 父子关系、继承、依赖和特性引用正确解析 |
| 可用 | 能在向导/卡面选择、保存、重开、升级及适用的导出中使用 |

各资源包、类别分别记录这五层状态。数量增长不能代替关联正确，读取成功不能代替业务可用。

## 三、两库发现与加载

### 3.1 5etools-cn

使用仓库实际索引发现职业、法术分卷，当前已核实入口为 cn2.0 分支的 data/class/index.json 和 data/spells/index.json。禁止仅列举本地职业或只加载 PHB/XPHB。

职业分卷里的 class、subclass、classFeature、subclassFeature 都要处理，并把引用与独立特性集合关联。物品文件包括 items-base.json、items.json 和 magicvariants.json。

其他目标类别由经过核实的文件清单管理。charcreationoptions、rewards、cultsboons、optionalfeatures 等候选文件及其顶层键必须逐项核实后接入，不把候选名称当作已完成加载的证据。

### 3.2 tjliqy/homebrew

当前已核实 master 分支有 class/、subclass/、collection/ 等目录；其文件布局不同于核心库，需要独立发现适配器。

1. 优先核实仓库生成索引是否覆盖目标类别、集合文件以及选定修订。
2. 若无合适索引，通过文件树或目录 API 发现文件，处理分页、截断、限流、重试和取消。截断响应不能标记为发现完成。
3. 缓存带仓库、分支/提交、路径和类别的发现清单；允许部署端生成或自托管清单，避免每次浏览器启动遍历 GitHub。
4. 按文件实际顶层集合识别类别，读取 _meta 和依赖声明，不仅凭目录名分类。建立跨包依赖图并报告缺失项。
5. 接入资源包启用流程，按需加载文件与依赖；区分未启用、待加载、失败、部分可用和可用。

正确编码包含空格、分号及非 ASCII 字符的路径。不把访问凭据写入前端构建。缓存清单兜底需展示修订及刷新失败状态。

### 3.3 统一处理流程

发现清单 → 资源包与依赖选择 → 文件读取/缓存 → 条目校验 → 继承与引用解析 → Catalog → 业务适配 → 向导/卡面/引擎。

- 两库共用后半段管道，每条记录保存包、书源、原始身份、仓库路径和修订。
- 并发、重试和超时有上限；单条异常隔离，失败包不阻塞无依赖的其他包。
- 原始文件缓存与解析缓存分开版本管理；适配器升级后使不兼容结果失效。
- 后台刷新不仅写缓存，也更新 Catalog 并通知页面；持有旧数组不算刷新成功。
- 汇总预期文件数、成功数、失败数、条目数和缺失引用，不能忽略 loader 返回的 warnings。
- 已选资源尚未取得时展示等待或失败状态，不显示成“没有这个选项”。

### 3.4 镜像与离线

缓存有效时优先缓存；网络顺序为显式配置的源/同源目录、已验证镜像、原仓库或 CDN。两库独立配置和降级，不能把 Homebrew 请求发往核心库兜底。

保留 NEXT_PUBLIC_5ETOOLS_BASE_URL、NEXT_PUBLIC_HOMEBREW_BASE_URL 配置入口，并支持自托管发现清单。https://5e.kiwee.top 仅作为待验证候选，目录兼容、CORS、修订一致性和目标网络性能实测通过后才能默认启用。

离线仅保证已缓存的资源。首次访问无缓存需明确报告缺失。完全自托管需要应用、两库所需文件、清单与完整依赖，不能仅靠修改一个地址。

## 四、身份、版本和特性关联

### 4.1 稳定身份与存档

- 身份包含包、类别、书源及原始条目标识；特性还需父职业、子职、等级等消歧字段。显示名不是唯一依据。
- 分类迁移必须保存旧 ID 映射；现有 item 改为 baseitem 的存档影响要专项验证。
- 不同版本、书源和包的同名资源不能按名称直接合并；歧义需要明确选择。
- 存档保存来源身份与必要的原文/已解析效果快照；上游删除或离线时不自动替换成另一版本。
- 背包实例 ID 与物品定义 ID 分开；装备、同调引用实例，经 itemId 获取定义。移除实例后残留 ID 不得继续贡献效果。

### 4.2 继承、引用与职业组装

- _copy/_mod 支持跨文件、跨包、解析顺序和循环检测。未知修改保留原始数据并标记未完整解析，不能静默视为成功。
- 特性字符串/对象引用按来源约定解码，包括默认书源、父职业书源、子职书源、等级和可选分支。
- 子职挂载依靠明确身份、父职业和书源；中英文别名用于查找，不能用 includes 模糊包含决定归属。
- 子职和特性出版物可以不同于父职业。不得用 feature.source === class.source 作为通用门槛。
- 各兼职职业分别按自身等级和子职处理。可选特性必须确认已经选择才能生效。
- 完成进度表、等级特性、施法配额、选择项和资源恢复的业务装配。缺失内容不能直接套用本地相似职业。

## 五、计算覆盖与兼容要求

公共数据同时包含结构字段与只供阅读的段落。内容可见和自动计算必须分别标记。

每项效果记录“已自动计算、部分自动计算、待人工处理”、公共来源及适配版本。优先使用可靠结构字段，其次使用绑定公共身份与版本的 Mechanics Overlay；受限文本解析必须有真实样本和误判测试。

禁止用宽泛的“最多 N 件”正则决定同调上限，或把任意 ability 数字视作属性设定值。无法确定时保留原文，列为待人工处理。此降级不等于机制验收通过；约定必须自动计算的项目未完成时，阶段不能宣称完成。

### 5.1 向导与法术

- 保留背景 enableLegacyAsi 显式开关并持久化；2014 背景默认不提供 2024 式加点。
- 种族固有加值与自由选择按来源处理；支持 choose 不代表所有 2024 种族都有属性加值。亚种/血系术语按来源语义展示。
- 专长类别与前提条件分别处理；未知前提可见，不自动视为满足。
- 法术职业归属采用统一身份与别名映射，兼容现有中英文选择器，不改写原名。
- spellsByLevel 的新增、替换资格/数量、学派和例外按具体职业及版本判定，不统一假定每级可替换一个。
- getSpellDefinition 支持稳定 ID 与旧引用；比较前解析身份。逐级历史、准备法术、法术书和最终法表保存重开后保持一致。
- 契约魔法与常规法术槽独立保存和恢复；兼职折算、准备数量、休息恢复量按相应版本处理。

### 5.2 装备、工具和魔法变体

- 保留原始价格单位，转换展示值；护甲 AC、敏捷上限、力量要求、隐匿劣势及豁免条件一起验证。
- 魔法变体是生成规则，处理 requires、excludes、inherits 及基础装备组合后才可当成具体装备。实例身份同时保留模板和基础来源。
- bonusAc、施法 DC/攻击、武器加值、属性增加、属性设定、属性上限分别适配，防止继承和重复字段导致双算。
- 生效检查穿戴/持握/装备、同调、职业限制与条件。已同调不自动等于正在使用；卸下但仍同调的物品不应继续提供穿戴效果。
- 设定型效果按原文规则处理，不降低本来更高的属性；常规封顶与上限突破分层，手动覆盖最后生效。
- 工具熟练、专精与优势按实际特性和条件处理，不能根据职业名赋予全部工具专精。
- 未知必需字段应标记不完整，不能填入看似合法的默认值后参与计算。

### 5.3 同调

基础上限为同时同调 3 件需要同调的魔法物品；普通装备、无需同调的魔法装备不占用同调名额。

上限由基础值与已获得特性共同决定，覆盖公共职业、子职、种族、专长和已选择的可选特性。固定上限与额外槽位按其原文规则组合并去重，保留书源、等级和效果追溯，不能依赖本地核心职业名单。

界面显示“已同调 X / 当前上限 Y”及上限来源。只有 X > Y 时提示“超出当前同调上限，需由 DM 确认”，保留操作，不固定在第 4 件警告。尚未自动支持的特性允许带来源说明的人工上限覆盖。

覆盖重复 ID、定义与实例混用、移除物品、数量为零、跨书源子职、扩展职业和未知同调要求。未知要求不能直接判为“不需要同调”。

### 5.4 赠礼、恩惠与人工覆盖

赠礼、祝福和恩惠统一检索，在卡面提供添加、移除与原文。属性上限、HP 等按具体条目处理，不把所有传奇恩惠概括成相同数值效果。

Trace 并列系统值与手动值；验证手动属性覆盖会刷新适用的 AC、HP、攻击、法术与技能派生结果，而非只改变显示数字。

## 六、容错和真实状态

1. 非关键展示字段可安全回退；缺环阶不能默认成为合法戏法，缺父职业不能随意挂载，缺书源不能伪装 PHB。
2. 非中文条目显示原名；关键字段缺失的条目可供阅读，但参与选择/计算的限制要明确。
3. 文件、条目、依赖错误分别记录来源、原因及重试入口；仅 console warning 不够。
4. 至少区分加载中、可用、部分可用、失败、缓存兜底。“任一核心类别成功”不能代表核心齐备。
5. complete 仅指当前已启用范围必需文件和关系处理完成；自动计算覆盖单独报告。
6. 资源包发现失败、未启用和无此资源是三种不同状态。

## 七、实施顺序和验收交付

已有模块可复用，但按以下标准重新验收。一个步骤可拆小步，汇报中明确小步完成不等于整阶段完成。

| 步骤 | 工作内容 | 必须交付的证据 |
|---|---|---|
| 1. 双源清单与真实状态 | Homebrew 发现与启动/资源包加载，双源诊断 | 两库真实文件载入；Homebrew 含本地未录入的职业、子职和特性；部分失败不误报 complete |
| 2. 职业与特性组装 | 继承、引用、父子关系、进度和选择项 | 扩展职业进入向导；跨书源子职正确挂载；按等级取得特性 |
| 3. 身份与存档兼容 | 来源消歧、旧别名、实例引用与快照 | 旧存档、同名不同书源、分类变更、缓存刷新和上游缺项后不丢引用 |
| 4. 法术全链路 | 职业归属、逐级选择/替换、最终法表和槽位 | 真实公共法术完成建卡、升级、保存重开；双版本与兼职分别验证 |
| 5. 装备与同调 | 变体实例化、条件效果、动态上限和追溯 | 真实公共装备穿脱/同调正确；扩展特性提高上限；无需同调装备不占名额；无重复加值 |
| 6. 其余目标类别 | 种族、背景、专长、工具、赠礼、可选特性等 | 每个目标类别可检索、选择和保存；未知机制有待办与人工入口 |
| 7. 高可用与性能 | 增量加载、刷新、镜像与自托管 | 冷缓存、热缓存、断网、坏文件、限流、旧修订均有可重现结果 |
| 8. 解耦与归档 | 应用配置迁移、旧依赖清除、备份归档 | 前置验收通过；业务无旧数据依赖；迁移与构建通过；体积耗时前后测量 |

## 八、测试与最终完成条件

### 8.1 测试层次

- 单元测试：身份消歧、引用解码、继承、条件效果、失败隔离和数值边界。
- 真实数据契约测试：从两个指定仓库摘取精简样本，记录路径、提交/修订和摘取方式。覆盖核心与扩展职业、跨书源子职、中英文引用、复制依赖、魔法变体和非标准条目。
- 集成测试：发现 → 文件 → Catalog → 业务适配 → 引擎/存档；不能全部使用手工构造的理想对象。
- 浏览器验收：空缓存进入、启用扩展包、选择职业特性、生成卡面、升级、重开和断网；确认后台载入后界面更新。
- 构建与性能：执行项目实际生产构建，记录耗时、体积、请求数、下载量和目标网络加载时间。取得基线后量化指标；“秒开”“削减 80%”不再是未经测量的承诺。

### 8.2 完成标准

必须同时满足：

1. 两库约定修订及目标类别的发现清单完整，截断、失败与排除项明确。
2. 已启用资源及依赖可用，扩展内容不依靠本地恰好存在同名条目才能工作。
3. 身份、书源、版本、关联、特性等级和选择历史正确，旧角色迁移及保存重开通过。
4. 约定必须自动计算的机制通过验证；其他覆盖状态、原文和人工入口可见。降级清单不隐藏，不等同于完整自动计算。
5. 原始语料可回查，2014/2024 及跨包内容不误替换。
6. 断网或单点失败不丢角色，无缓存的未取得资源明确标示。
7. 手动开关、人工覆盖和 Trace 通过实际业务场景验证。
8. 安全解除旧依赖后再归档，生产构建与性能测量通过。
